## 0. 一句话结论

当前产品**功能闭环已完整**（算法、调度、复习流、富文本、三档响应式均达标），真正的短板不在"功能多少"，而在
**"用户投入的资产没有任何保全手段、也没有任何回报机制"**——即**数据会丢、删了回不来、坚持了没人看见**。
因此下一阶段主线不是加功能，而是**补齐"资产安全"与"长期反馈"两条腿**，并顺手清掉一个极低成本的对外信任缺口（占位图标）。

## 1. 用户价值诊断：当前最致命的 3 个流失缺口

判断依据均来自代码与交付记录的**客观事实**，非主观体感。

### 缺口 A：数据资产零保全 —— 换机/重装/清除数据 = 100% 永久丢失（最高危）

- **事实依据**：数据库 `ebbinghaus_memo.db` 位于 App 私有目录（`AppDatabase.getInstance` 的 `databaseBuilder` 未指定外部路径），
  `exportSchema = false`，全项目**无任何导入/导出/备份入口**，`AndroidManifest` 无 `allowBackup` 声明。
- **后果链条**：Android 卸载应用即删除私有目录 → 用户换机、重装、清数据、刷机，**全部知识点 + 笔记 + 复习档位 + 复习历史一次性归零，且不可恢复**。
- **为什么是"一票否决"**：知识类应用的价值 = 用户累积的存量内容。存量越多，损失越痛。
  更糟的是它形成**负向激励**：用户越认真用（积累越多），越不敢承担丢数据的风险，反而越早放弃；
  而"用一天就走"的用户毫无损失。这是**唯一不可逆**的缺口，其它缺口都能靠后续迭代补救，这个不能。
- **量化口径**：一次卸载事件的数据存活率 = **0%**；当前无任何迁移/恢复路径。

### 缺口 B：无成就反馈闭环 —— 长周期复习注定动力衰减

- **事实依据**：`ReviewTaskEntity` 仅有聚合字段 `stageLevel / dueDate / lastReviewDate / reviewCount / updatedAt`，
  **没有任何"按日复习事件"记录**；UI 侧**无统计页、无连续打卡、无热力图**（全项目无相关组件）。
- **为什么致命**：本产品的复习周期是 **1/2/4/7/15/30 → 60 天**，本质是**跨度数月的高频长期行为**。
  周期越长，越依赖"可见的正反馈"维持；而产品当前**连"我今天复习了几条、连续坚持了几天"都看不到**。
- **叠加放大**：原需求明确"多天未登录**免惩罚**合并顺延、不标逾期"——这是好设计，但**它同时消除了唯一的负反馈**。
  于是"无负反馈（免惩罚） + 无正反馈（无统计）"= **用户没有任何回来的理由**。这是长期留存的结构性漏洞，非体验瑕疵。
- **量化口径**：当前用户可获得的"进度感知"= 0 项指标；无法回答"我坚持了多久、效率如何"。

### 缺口 C：删除不可逆 —— 高价值内容一次性损毁

- **事实依据**：`KnowledgeMemoDao.deleteById` 为**物理 DELETE**，配合 `ReviewTaskEntity` 的 `ON DELETE CASCADE`，
  一次删除同时抹掉该知识点**全部复习进度与历史**；当前防线**仅有一层二次确认弹窗**（`DeleteConfirmDialog`）。
- **为什么痛**：知识点的价值随时间**累积**（笔记越写越多、档位越走越高），误删的成本与"沉没投入"成正比。
  二次确认只能防"手滑点错一次"，**防不了"确认后才发现删错"**——而这恰恰是最常见的事故形态。
- **量化口径**：当前误删恢复率 = 0%；一个 60 天档位的知识点被删，等于损失 6 次以上的复习投入。

## 3. P0 优先级论证：为什么是"现在做"

### E01 全量数据导出/导入 —— 唯一"不可逆损失"的解药

- **不做会怎样**：用户换机/重装后 **100% 数据归零**，且无任何补救路径。这不是体验问题，是**产品可信度问题**：
  用户一旦意识到"这 App 会丢我的东西"，会主动降低投入甚至卸载，形成"越早走越安全"的反向筛选。
- **做了带来什么**：
  1. 把"数据存活率 0% → 100% 可迁移"，直接消灭**唯一不可逆**的流失风险；
  2. 是 E02 自动快照、E12 导入的**公共底座**（一次投入，三处复用）；
  3. 让用户"敢投入"—— 存量内容越多越离不开，**直接抬高迁移成本（正向的）**。
- **为什么是现在**：成本 M、**零 schema 变更**（走 SAF，无需任何权限），是当前**性价比最高的风险消除动作**。

### E04 复习统计 + 连续打卡 —— 长期留存的发动机

- **不做会怎样**：产品周期长达 **60 天**，用户却**看不到任何进度回报**；叠加"免惩罚顺延"消除了负反馈，
  等于**既没奖励也没惩罚**，用户缺乏回来的理由，长期留存必然衰减。
- **做了带来什么**：
  1. 补上唯一缺失的**正反馈闭环**（连续天数 / 累计复习量）；
  2. 让"免惩罚顺延"这个好设计**不再被浪费**——有打卡记录，用户才愿意"接上断掉的链子"；
  3. 是 E05 热力图的**数据基础**。
- **为什么是现在**：它是**唯一需要 Room 迁移（新增 `review_logs`）**的 P0 项，迁移越晚做，历史数据越难补齐
  （早期不记录事件，**上线前的复习行为将永久无法回填**）。因此必须**尽早立项**，让迁移一次到位。

### E07 瞬时撤销 —— 最低成本的"不可逆"修复

- **不做会怎样**：`deleteById` 物理删除 + `CASCADE` 抹掉全部复习历史，仅靠二次确认防不住"确认后才后悔"。
- **做了带来什么**：删除后 5 秒内可恢复，**用一个 Snackbar 的工程量**把最常见的误删事故挡在门外。
- **为什么是现在**：成本 **S**、**零迁移**（内存暂存即可），复用已交付的 Snackbar 通道，
  是**当天就能做完**的止血动作；同时为 E06 回收站争取时间。

### E00 正式应用图标 —— 近零成本的信任补齐

- **不做会怎样**：占位图标让产品在桌面与应用市场呈现"半成品"观感，**在用户第一次打开前就已经扣分**。
- **做了带来什么**：成本 S、零逻辑改动，直接提升"这是成品"的感知与品牌辨识度。
- **为什么是现在**：**性价比最高**的收尾项，无任何依赖与风险，适合与 E01 同批次顺手完成。

## 4. 明确建议"不要做"的需求（含红线判定）

| 需求 | 结论 | 理由（对齐产品红线：**轻量、离线优先、不引入冗余大型三方库**） |
|---|---|---|
| **E17 多设备云同步** | **不做** | 需要账号体系 + 服务端 + 网络权限，**直接摧毁"离线单机、零网络权限、无账号"这一核心卖点**，且从"工具"变成"服务"，运维成本不可控。**替代方案**：E01 导出文件 → 用户自选网盘手动同步，用 5% 的成本覆盖 80% 的诉求。 |
| **E15 OCR 拍照录入（自研/ML Kit 方案）** | **不做** | 需引入 ML Kit 等**数 MB 级三方库**（当前 release 仅 **1.53 MB**，等于体积翻数倍），并申请 `CAMERA` 权限，**同时违反"轻量"与"零权限"两条红线**。**替代方案**：引导用户用系统相机 + 输入法剪贴板，或仅做"系统级零依赖"方案再评估。 |
| **E16 系统通知提醒（默认开启）** | **默认不做** | 与原始需求 R3"**免申请系统级高侵入通知权限**"**直接冲突**，是该需求的设计前提而非遗漏。**若确要做，必须严格约束**：用户显式开启后才申请权限、未开启时不得弹权限框、关闭后不得残留 Channel。 |
| **引入第三方重型富文本/全量编辑器框架**（如自研 Markdown 之外的通用编辑器库、WebView 富文本框架） | **不做** | 现有 `marked.js` + `KaTeX`（离线内置，共约数十 KB）已满足 Markdown + LaTeX，**自研管线已解决"公式保护"关键难题**；再引入重型编辑器属重复建设，直接推高体积与维护面。 |
| **动态取色（Material You `dynamicColor`）默认开启** | **不做（保持默认关闭）** | 会削弱品牌色一致性，且需 API 31+ 分支；当前 `EbbinghausTheme` 已将其默认置 `false`，**维持现状即可**，不宜改为默认开。 |

## 5. Roadmap 建议（三期）

### 第一期 · 止血与信任（近期，1 个迭代）

- **目标**：消灭**不可逆损失**，补齐对外基本体面。**不引入任何 Room 迁移，零新增重型依赖**。
- **包含需求**：**E01**（导出/导入）、**E07**（瞬时撤销）、**E00**（正式图标）、**E03**（深色模式手动切换）、**E10**（排序）。
- **验收口径**：
  1. **导出文件在"全新安装 + 空库"上可完整还原**：知识点条数、标签、内容、笔记、`stageLevel`、`dueDate`、`reviewCount` **逐字段相等**（自动化往返测试）；
  2. 删除后 5 秒内撤销可 100% 恢复（含关联复习进度）；
  3. 深色模式三种取值（浅/深/跟随系统）切换即时生效且**重启后保持**；
  4. **回归硬指标**：`./gradlew test` 全绿；release APK 体积增幅 **< 200 KB**；`AndroidManifest` **零新增权限**。

### 第二期 · 留存引擎与效率（中期，1~2 个迭代）

- **目标**：建立**正反馈闭环**，同时完成**首次 Room 迁移**（一次性做好）。
- **包含需求**：**E04**（统计/打卡）、**E05**（热力图）、**E06**（回收站，含 `deletedAt` 迁移）、**E08**（标签管理）、**E11**（批量操作）、**E09**（桌面小组件）。
- **验收口径**：
  1. `review_logs` 记录与打卡/统计/热力图三处展示**数据一致**（同源同口径）；
  2. **Room v1→v2 迁移有 `MigrationTestHelper` 自动化测试**，且**旧库升级后原有数据零丢失**（关键：迁移必须可测、可回滚验证）；
  3. 回收站保留 30 天，到期自动清理，还原后复习进度完好；
  4. 标签重命名/合并**在事务内完成**，中断不产生半更新状态；
  5. 小组件在**不申请任何权限**下可显示今日待复习数并点击进入。

### 第三期 · 扩展与输入（远期，按需评估）

- **目标**：降低**冷启动迁移门槛**与**录入成本**，全部以"零新增权限 + 轻量"为前提。
- **包含需求**：**E12**（CSV 导入）、**E13**（分享卡片）、**E02**（自动快照）、**E14**（语音，仅走系统 IME）、**E16**（通知，**严格 opt-in**）。
- **验收口径**：
  1. CSV 导入**幂等**（重复导入不产生重复条目）且失败可回滚；
  2. 分享卡片**离线生成**，无网络依赖；
  3. 自动快照不阻塞 UI，失败可感知；
  4. **E16 必须满足**：未显式开启时**不申请、不弹框、不建 Channel**（否则该需求一票否决）；
  5. **E15（OCR）在本期仍不进入排期**，除非能找到**零三方库、零 CAMERA 权限**的方案。

## 6. 附录：判断"是否触发 Room 迁移"的 schema 事实

| 实体 | 现有字段 | 对本次规划的影响 |
|---|---|---|
| `KnowledgeMemoEntity` | `id, content, notes, tags: List<String>, createdAt, updatedAt` | **无 `deletedAt`** → E06 回收站**必须迁移**；`tags` 为**单列分隔符拼接**（`Converters` 用 `U+001F`）→ E08 标签管理只需**扫描回写**，**无 schema 变更** |
| `ReviewTaskEntity` | `id, memoId, stageLevel, dueDate, lastReviewDate, reviewCount, updatedAt` | **仅有聚合值，无按日事件** → E04 统计/打卡/热力图**必须新增 `review_logs` 表（迁移）** |
| `UserSettingsEntity` | `id, dailyReviewLimit, lastActiveDate, lastPromptedDate` | **无主题字段** → E03 深色模式**若写 Room 则迁移**；**改用 `SharedPreferences`/DataStore 即零迁移**（推荐） |
| `AppDatabase` | `version = 1, exportSchema = false` | 尚无任何 `Migration`；**首次迁移（第二期 E04/E06）应同时补 `exportSchema = true`**，否则后续迁移无基线可校验 |
| `EbbinghausTheme` | `darkTheme = isSystemInDarkTheme()`，**`DarkColorScheme` 已完整定义** | **深色"跟随系统"实际已生效**，"没有深色模式"的准确表述应为**"缺手动切换与持久化"** → E03 成本因此为 **S** |
